---

## 1. Objective
Learn how advanced SIEM correlation rules combine disparate telemetry streams (Nginx HTTP access logs and Linux `auditd` system call records) into a high-confidence, composite security incident (Level 11 Critical Alert), and analyze why correlated multi-source evidence is superior to isolated single-source alerts.

## 3. Scenario
A high-severity composite alert triggers: **SOCForge (DET-COR-001): Multi-Source Correlation: High-confidence web exploit followed by immediate system command execution**. You must reconstruct the complete attack narrative across multiple indices and determine the exact timeline of the intrusion.

---

## 4. Attack / Event Generation
Execute the correlated attack scenario from the Linux Attack Host:

```bash
# Connect to Attack Host via Bastion
ssh -i ~/.ssh/socforge_key -o ProxyJump=ubuntu@<BASTION_PUBLIC_IP> ubuntu@10.10.20.114

# 1. Trigger web command injection against DVWA
curl -s "http://10.10.30.148:8000/vulnerabilities/exec/?ip=127.0.0.1%3Bwhoami&Submit=Submit"

# 2. Trigger immediate host system command execution
ssh -i ~/.ssh/socforge_key -o ProxyJump=ubuntu@<BASTION_PUBLIC_IP> ubuntu@10.10.30.148 'sudo -u www-data /usr/bin/whoami'
```

---

## 5. Expected Telemetry
- **Generating Host**: `SOCForge-web` (`10.10.30.148`).
- **Telemetry Streams**:
  1. `socforge-nginx-access-*`: Rule `100102` (Level 9).
  2. `socforge-auditd-*`: Rule `100501` (Level 7).
  3. `wazuh-alerts-*`: Composite Correlation Rule `100601` (**Level 11 Critical**).

---

## 6. Investigation Steps

1. **Locate the Composite Correlation Alert**:
   - In OpenSearch Dashboards Discover, select: `wazuh-alerts-*`.
   - Search for:
     ```text
     rule.id: "100601"
     ```
   - Note the rule level (`11`), rule description, and triggered time window.
2. **Examine the Triggering Precursor Event**:
   - Expand the document and note `rule.firedtimes` and `previous_output` or search for Rule `100102` in `socforge-nginx-access-*` within the same 30-second window.
3. **Examine the Correlated Syscall Event**:
   - Search `socforge-auditd-*` for the `execve` event that matched `data.audit.euid: "33"`.
4. **Compare Confidence**:
   - Evaluate why having both the HTTP request AND the operating system process creation elevates the event from a suspected probe to a confirmed root compromise.

---

## 7. Investigative Questions
1. **What two distinct log sources were correlated by the SIEM engine?**
2. **What was the time delta (in seconds) between the web request and the system process execution?**
3. **Why is an isolated HTTP access alert (Level 9) less actionable than the correlated alert (Level 11)?**
4. **If an attacker sends 1,000 command injection probes to a hardened Nginx server that blocks them with 403 Forbidden, will the correlation rule trigger? Why or why not?**

---

## 8. Expected Findings & Solutions
- **Correlated Sources**: Nginx Web Access Log (`/var/log/nginx/access.log`) and Linux Kernel Audit Log (`/var/log/audit/audit.log`).
- **Time Window**: Less than 30 seconds.
- **Superiority of Correlation**: Single-source web logs produce high false alarm rates because web scanners frequently probe non-vulnerable servers. Syscall correlation confirms that the web process *actually executed* the injected payload in the kernel, achieving 99%+ true positive confidence.
- **Blocked Probes**: The correlation rule will **not** trigger on blocked probes because no auditd `execve` event will be generated by the operating system.
